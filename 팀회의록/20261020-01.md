- **일시**: 2026년 10월 20일(화) 오전
- **회의 주제**: 데이터 전처리 최적화, 벡터 DB 비교(PostgreSQL vs Chroma), LLM/RAG 모델링 및 근거 데이터 매칭 방안 논의
- **참석자**: 권우, 준, 민지(비대면/작업 중), 정빈, 기타 팀원

## 1. 주요 안건 및 진행 상황 요약

### 1.1 벡터 DB 구축 및 속도 테스트 현황
- **권우 진행 상황**:
  - 기존 Chroma DB 외에 **PostgreSQL(pgvector 확장)**을 활용한 벡터 검색 성능 테스트 진행.
  - JSON 단일 원본 파일(약 2MB)을 통으로 입력 후 PyTorch + GPU 연동하여 임베딩 진행.
  - **소요 시간**: 임베딩 약 5~10분, DB 저장까지 포함해 총 30~40분 소요(기존 대비 대폭 단축).
  - 로컬 환경 설치는 독립된 가상환경(Python 3.10)에서 구축했으며, 일반 인스톨러 및 라이브러리 충돌 이슈 해결 완료(팀 공유 예정).
  - 파이썬 버전의 경우 팀 기준 버전(3.11/3.12 계열)과 큰 충돌 없이 호환 가능할 것으로 판단.

### 1.2 데이터 전처리 및 LLM 메타데이터 추출 이슈
- **문제점**:
  - 회의록 원본 데이터(JSON 내 HTML 태그 포함 형태)의 키워드 및 요약 메타데이터를 LLM으로 추출하는 데 시간이 과도하게 소요됨.
  - 현재 로컬 처리 시 12시간 동안 약 16~17%만 진행되어, 전체 작업 완료까지 3~4일 이상 걸릴 것으로 예상.
- **개선 및 대응 방안**:
  - **전처리 텍스트 재활용**: 원본 HTML 전체를 LLM에 던지기보다, 이미 전처리(정제)해 둔 한 줄 단위 텍스트 파일을 적극 활용.
  - **어트리뷰트 정리**: JSON 파싱 시 불필요한 필드(`utterance_preview` 등)는 제외하여 데이터 경량화.
  - **플러그인/형태소 분석기 모색**: LLM 호출 대신 파이썬 형태소 분석 라이브러리나 키워드 요약 플러그인을 활용해 전처리 속도 개선 시도.
  - **상용 API 활용(제미나이/GPT Plus/Codex 등)**: 대외비 유출 방지 가이드라인을 준수하는 선에서 샘플 단위 분할 및 외부 도구 병행 검토.

### 1.3 '근거 회의록' 표기 방식 및 원본 매칭 논의
- **대회 요구사항**: 타 지방의 흐름 파악 및 향후 예측 시 **"판단에 사용한 원문 구간/근거 회의록(회의명, 일자, 발언 문장)"**을 제시해야 함.
- **논의 내용**:
  - 원본 JSON(HTML 포함 태그) vs 정제된 메타데이터 파일 중 어떤 것을 원문 구간으로 볼 것인가?
  - **결론 도출 방향**: 
    - 최종 사용자/평가자에게 불필요한 내부 태그 전체를 보여줄 필요는 없음.
    - 정제된 전처리 데이터의 **회의명, 일자, 실제 발언 문장(Context)**을 매칭하여 근거 문장 구간으로 표시하는 것이 적절함.
    - 대회 주최 측 Q&A 게시판에 "원문 구간 제시 기준(태그/순번 표기 여부 등)"을 구체적으로 질의하여 명확히 확인하기로 결정.

### 1.4 RAG 파이프라인 및 개발 아키텍처 합의
- **검색 및 모델링 플로우**:
  1. 사용자 질의 입력 (키워드/자연어 문장)
  2. 로컬 LLM을 통한 질의 분석 및 키워드 추출
  3. 벡터 DB 유사도 검색 및 랭킹 산출
  4. 검색된 근거 문맥(Context)을 다시 로컬 LLM에 주입하여 답변 및 향후 예측 생성
  5. 최종 결과를 정해진 규격(JSON 형태)으로 출력
- **최종 결과물 UI**: 로컬 웹 인터페이스(FastAPI/Streamlit 등 웹 데모)를 구축하여 시연 및 포트폴리오용 URL 확보 추진.

## 3. 주요 결정 사항 (Decisions)

1. **일정 관리**: 오늘(화) 중으로 전처리 작업을 일단락하고, 내일(수)부터 각자 본격적인 LLM 모델링에 들어간다.
2. **임베딩 모델**: 1차 모델링 단계에서는 공지사항에 공유된 **단일 임베딩 모델로 통일**하여 작업하고, LLM 모델은 각자 자율적으로 적용 후 가장 우수한 파이프라인을 최종 채택한다.
3. **최종 출력 규격**: 각자 모델을 구성하되 최종 출력 데이터는 합의된 **동일한 JSON 규격**을 만족해야 한다 (규격은 추후 공지).
4. **대회 공식 문의**: 원문 구간 표출 방식에 대해서는 대회 Q&A를 통해 공식 확인을 거친다.
