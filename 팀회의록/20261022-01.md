## 3. 주요 기술 논의 및 의사결정

### 3.1. DB 선택 및 벡터 저장소 비교 (Chroma vs. PostgreSQL)
- **PostgreSQL**:
  - `JSONB` 형식 활용 시 속도 향상 및 관계형 데이터/메타데이터 관리가 용이함.
  - SQL 도구를 통해 적재 중간에도 테이블 데이터를 시각적으로 직접 확인 가능.
- **ChromaDB (벡터 DB)**:
  - 대용량 임베딩 데이터 적재 시 중간 모니터링이 어렵고 스키마 변경 시 전체 재작업 부담이 있음.
  - **대응책**: 청킹(예: 5,000개 단위)마다 중간 커밋/저장 로직을 두어 중단되더라도 기존 저장분을 보존할 수 있도록 파이프라인 개선.
  - Docker 환경을 이용해 환경 격리 및 배포를 용이하게 처리한 사례 공유.
- **적재/임베딩 속도 측정**:
  - 임베딩 소요 시간 및 추후 질의 정확도(Accuracy)를 비교 지표로 기록(이미 진행된 작업은 굳이 재측정하지 않고 유지).

### 3.2. 최종 출력(Output) 스키마 정의
- **출력 포맷 요구사항**:
  - "후속 논의 흐름 및 향후 예측을 항목별 서술형으로 제시"라는 요구 조건 검토.
  - 단순 텍스트 챗봇이 아닌, **통계 + 지도 시각화 + 흐름(테이블/리스트) + 향후 예측(서술형)**이 종합된 대시보드 형태의 JSON 스키마를 구성하기로 합의.
  - 구글 드라이브에 공유된 샘플 JSON 파일 기준으로 개발하되, 프론트엔드 연동 단계에서 세부 필드 유연하게 조정 가능.

### 3.3. 시스템 아키텍처 연동
- 백엔드/서빙: FastAPI 또는 Streamlit 활용 논의 (간단한 검색 및 프론트 시각화 데모 연동).
- 비교 평가용 스크립트 작성 필요: 특정 키워드/질의 입력 시 LLM 파이프라인 결과의 신뢰도를 점검할 수 있는 평가 스크립트 구축 예정.
